# 同じ業務を、原文と訂正を残してまとめる

画像とPDFに同じ仕事が載っていても、別々の業務として増えていた。保存前の候補からも「同じ業務とまとめる」を開き、既存の業務と手順の対応を確かめられるようにした。

一致する名前や作業が一つに特定できる場合に対応を提案する。担当、作業、判断、道具などが違う場合は、採用する側を人が選ぶまで保存しない。対応しない手順は独立した手順として残し、つながりを作り足さない。現在・将来、工場・拠点、期間が違う業務は統合しない。

双方の原文、元資料への参照、人の訂正を残す。業務間の受渡し、所属する活動、システムの関係も統合先へつなぎ直す。片方にだけある、対応済みの手順間の矢印は「資料の記載差・採用版は未確認」として扱う。人が挿入した手順を飛ばす通常経路に勝手に変えない。

保存は原文と取り消し用の差分を含めて一つのトランザクションで行う。確認中に別の保存が入った場合は、古い状態で上書きしない。統合履歴から元に戻せるが、統合後に関連する業務が編集された場合は、その編集を消さないよう取り消しを止める。

## 実画面での確認

2026年10月5日、既存データとは独立した`pdf-arrows-20261005`で検証した。画像だけのPDFとPNGの原図をgpt-6-lunaで直接読み取って作った候補を使用した。統合操作自体ではAIを呼ばない。

- PDFの委託検査は6手順。原図の「品質担当が受け取る」を、人が「購買担当が受け取り、Teamsで品質担当へ渡す」に訂正済みだった。PNGの5手順候補を選び、5組の対応と統合先の内容を採用した。6手順になり、購買担当、Teamsの受渡し、外部会社の内部が見えないことが残った。
- PNGにだけある受取から登録への矢印は、Teamsの受渡しを上書きせず、記載差として表示された。PDFとPNGの両方を、ページ選択から元の図で確認できた。
- 保存前の候補と保存済みの業務、保存済みどうしの両方で統合を保存した。画面を再読み込みしても図と原文が残った。
- 統合元のPNGを資料一覧から再び開くと「保存済み」になり、同じ統合先の業務を開いた。重複候補を再作成しなかった。
- 統合前の原文と担当の訂正履歴を確認し、統合を元に戻した。5手順のPNG業務と6手順のPDF業務が戻り、別の受注業務の未保存候補も保持された。再読み込み後も保持された。

単体テストでは、対応の重複、範囲の違い、手動の受渡し、SQLite保存後の復元、元ファイルのバイト列、従来の編集履歴、並行保存、後続の編集を確認した。300業務を持つ合成グラフでも統合先の二業務だけを変更することを確認した。このテストは実AIによる300件入力の検証とは別であり、実入力の蓄積は現在168業務で継続中。

## 制約

意味が似ていても、別の表現の手順を自動で同一と確定しない。対応は人が選べる。異なる内容は手順ごとに採用する側を選ぶ方式で、項目ごとの混合編集は統合後の手順編集で行う。取り消し用の差分は現時点ではプロジェクトの知識データに保存する。繰り返し大量に統合する場合の履歴分離は、将来のリポジトリ実装の検討事項として残る。Snowflakeへの実接続は行っていない。原資料と画像は、保存先に依存しない資料ID・ページIDで参照する。
