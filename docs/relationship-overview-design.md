# まとまりの関係から会社を読む

会社の入口では活動同士、システムの入口では役割ごとのまとまり同士の関係を表示する。最初から数百の業務や全てのシステムを並べない。活動を選ぶと前後の活動と仕事を読み、システムのまとまりを選ぶと三つずつ道具を開く。他の種類はまとまりのまま残し、種類をまたぐ情報の受渡しを読めるようにする。

道具を選んだ後は、その道具と直接つながる道具を表示する。支える活動、業務の例から仕事へ進め、情報・自動処理・判断は既存の詳細で読む。活動・道具の図は八要素・六関係を上限とし、個々の道具の周辺は六要素までとする。関係の続きは配置を保って切り替える。情報の受渡しと稼働の依存も切り替えて読み、一度に重ねない。図の件数は表示分と対象全体を区別する。線がないことを、実際の会社に関係がないという意味にはしない。

関係を選ぶと元の業務と原文を読める。活動の受渡し・参照、システム間の情報移動、稼働の前提となる依存を区別する。情報の線は移動元から移動先へ、依存の線は必要とする道具から必要な仕組みへ向かう。認証への依存を、業務の次の手順として読ませない。集約した線に推定・未確認が一つでもあれば点線で表示し、各根拠の確かさも残す。

分類名やノードの同時表示数だけで理解しやすさを保証するものではない。実画面で線と文字の重なり、移動前後の文脈、詳細を開いた後の情報量を確かめて調整する。

線には記録された情報名の一例と、参照・受渡し・接続の種類を短く表示する。長い名前や他の情報がある場合は省略を示し、線を開くと全ての根拠へ戻れる。異なる製品名などの後に同じ文字列がある場合、その共通部分を表示に使うことがある。情報の識別子や名前を統合する処理ではない。名前が未登録の情報を、内部IDで説明しない。

ノードが少ない図は外側の余白を減らし、選んだまとまりの仕事も同じ画面で読みやすくする。線の説明が重なる場合は、ノードを動かさず元の曲線に沿って説明の位置を調整する。関係の別ページも含めて位置を計算するため、同じノード範囲ならページを切り替えても配置を保つ。複雑な図の全ての重なりを解消する保証ではなく、元の方向・根拠と表示量を保った上での読み方の改善である。

活動を開いた先も、仕事の種類をまとまりとして表示する。記録された業務間の受渡し・参照を集約し、相手が別の活動なら活動のまとまりを残す。仕事のまとまりを選ぶと業務の例と一覧へ、線を選ぶと元の業務・手順・情報・原文へ進める。図は最大八まとまり・六関係とし、業務の一覧は六件ずつ、道具は必要な時に六件ずつ開く。業務を読んで戻った時には選んだまとまりと表示ページを保つ。

同じまとまり内の受渡しは自己ループを描かず、選んだまとまりの中で根拠を開く。相手のまとまりが未登録の受渡しは確認できる欄に残す。どちらも元の接続を消さない。同じ名前の種類を統合したり、複数の所属から一つを勝手に選んだりしない。線の根拠は三件ずつ、各根拠の関連業務は六件ずつ読める。

## 元の構造と表示を分ける

`lib/relationship-overview.ts`は保存済み構造から読み取り用の関係を作る。ノードは元の活動・分類・システムの識別子を使い、名前で同一視しない。集約関係は種類と端点で識別し、元の受渡し・データフローのID、業務ID、手順ID、情報ID、原文、個別の確かさを保持する。元の関係で手順が一つに決まる場合は、その手順から読み始める。複数なら勝手に手順を選ばず、業務を開く。システム依存には独立したIDがないため、記録されたシステムと前提の組、説明した業務を保持し、元の関係IDがあるようには扱わない。

同じ種類の内部関係は、種類同士の図の自己ループへまとめない。種類を開くと個々の道具間の関係を読める。配置の座標・表示予算・選択状態は画面側に置き、業務の原文や保存済みグラフを変更しない。表示の省略とデータの削除も区別する。

情報移動は選択した状態・部署・検索に合う業務を対象とする。認証などの会社共通基盤は別部署で説明される場合があるため、依存の根拠は同じ状態の業務から採る。現在の話の依存を将来案の説明へ混ぜない。共通基盤の台帳として登録された依存には業務IDがない場合もあり、その場合は原文未登録を表示する。

## 後でAPI・MCPから仮想的に辿るために

Snowflakeの例は、現在のSQLiteバックエンドを後で置き換え、保存された業務構造をMCPオブジェクトとして問い合わせる構想である。会社が利用するシステムとしてのSnowflakeと、アプリ自身の保存先は別の役割になる。今回、API・MCPの公開や保存先の移行は実装していない。

現在の`BusinessFlowRepository`はプロジェクトと業務改訂の読み書きを抽象化する。SQLiteは業務・ノード・エッジ・データフロー・改訂を保存し、会社の活動などは会社知識のJSONにも含まれる。画面は全体スナップショットを読み込む。これは、サーバー側で隣接関係だけを読むAPIが完成していることを意味しない。

後の読み取りAPIでは、プロジェクト・状態・改訂・部署・関係の種類を明示し、ノードIDから隣接要素と根拠をページ単位で取得する形を想定する。集約から元の関係へ戻れる識別子を返し、入力された事実、AIの推定、未確認、人の訂正を保つ。業務の家族IDで現在と将来案を対応づけ、表示位置や名前を識別子の代わりにしない。SnowflakeのビューやMCPオブジェクトへ移す場合も同じ契約で読めるよう、表示用の集約を保存形式に固定しない。

書込みを公開する段階では、原文・訂正・差分の確認と改訂の競合を扱う必要がある。今回の図の実装だけで、その書込みAPIや権限管理まで検証済みとは扱わない。
