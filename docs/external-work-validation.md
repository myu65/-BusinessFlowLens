# 社外の工程と、見える範囲

工程の担当と使う道具を分け、会社・委託先をシステムの名前にしない。社外の工程には`boundary`を持たせる。範囲、既知の相手、内部がどこまで見えるか、渡すもの、戻るもの、未確認の点、確かさ、根拠を記録する。既存の工程には新項目を自動設定しない。

`scope`はその工程を行う主体の範囲を表す。社内の担当が社外へ送る作業や、社外から受け取る作業まで社外の工程にしない。社外の検査工程の内部が見えなくても、分かっている受渡しは同じ情報グラフへ接続する。内部の方法・担当・道具・判定を推測で作り足さない。人が訂正した情報の一覧は自動補完で戻さない。

分類の修正は、構造化した社外の相手と完全一致する名前に限る。委託先のポータルやLIMSなど、別の名前で明示されたシステムは残す。会社名の文字パターンで一律削除しない。

画像のAI解釈は、元資料の文字として扱わない。AIが引用の先頭に画像解釈の目印を付けた場合も、その本文が解釈内で完全一致するかを確認し、推定として保持する。人の訂正は項目単位で残し、読み直した後も優先する。

検証には、架空の監査資料の品質担当→Outlook→外部検査会社→PDF成績書→Outlook→LIMSの流れを使う。画像PDFの各ページの画像とgpt-6-lunaの読取り、ページ間の食い違い、保存前のフロー、社外工程の受渡しと未確認、保存・再読込み、システム一覧、レポートを確認する。成績書の受取・登録を社内の合格判定に置き換えない。

単体テストでは、業者とポータルの区別、境界からの情報接続、推定の根拠、人の訂正、SQLite保存、レポート、現行と将来の比較を確認する。実AIの抽出結果の検証と、データの保存・表示のテストは分けて記録する。

残留溶剤測定の再調製からの戻りと、出荷保留中の解除依頼の表示は別のIssue #157で修正する。画像から矢印を読めていても、その後の業務構造の確認処理が正しく扱うかを別に検証する。

2026-10-05の実操作では、独立した`pdf-arrows-20261005`へ3ページの画像PDFをアップロードした。3ページとも文字抽出は0文字で、画像をgpt-6-lunaが読んだことを保存記録で確認した。委託検査の5手順を保存し、社外は検査工程だけ、社内の依頼・受取・登録は社内のまま、成績書受取を合格判定にしないことを確認した。会社の詳細画面でも社外の範囲と受渡しを読み、システム鳥瞰にはOutlookとLIMSだけが表示された。別のPPT検証プロジェクトでは、以前の誤分類を含む候補を読み直して訂正保存した。元からあった10プロジェクトの構造・原文・履歴は変更されていない。

単体305件、独立したSQLiteでのAPI回帰48件、型チェック、ビルドを通過。PDFの構造化はこの時点ではページ読取りの文章を経由しており、原図の直接参照と自然な言葉での訂正は続く改善で扱う。今回の確認をPDF抽出全般の精度保証とはしない。
