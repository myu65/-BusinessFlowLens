# 初めて使う人の入力・鳥瞰の改善と検証（2026-10-03）

「仕事の話を書く → 流れを見て補足・訂正する → 保存する」を最初の作業にした。会社探索と詳細調査は、保存した構造を使う入口として整理した。Issue #22 と #23 に対応する。

既存の `.data/ux-audit/` と現行画面を確認し、独立したプロジェクトでブラウザーを実操作した。これはエージェントによる操作・画面検証であり、独立した初見ユーザーを招いたユーザビリティ調査ではない。

## 変更した体験

- 主ナビゲーションを「話を入力」「会社の全体像」「詳しく調べる」に集約。詳細の4つの入口は、調べる画面に入ってから表示する。
- 入力欄の幅、16pxの本文、ボタンの大きさ、余白、フォーカス表示を統一。「1 話を書く」「2 流れを確かめる」「3 この流れを保存」を同じ作業面に置く。
- 保存前の候補は3手順ずつ表示。選んだ1手順の担当・道具・判断の根拠・結果・次の仕事を読む。訂正はまず「行うこと」「担当する人」「何が決まる・変わるか」の3項目で行い、部署・実行方法・条件などは必要時に開く。
- 保存操作を候補の上部に置き、スクロールしても届くようにした。未反映の本文と保存前の構造を明示し、訂正フォームを反映する前の保存も防ぐ。
- 続きの挿入は原文の句点や改行を保つ。原文と一意に対応しない場所は推測せず、本文での補足を案内する。情報の受取を出力扱いせず、作成・更新・送信を区別する。
- 狭い画面ではメモと流れを切り替える。3手順は縦に並べて隠さず、メモや選択を維持する。保存エラーも現在表示中の面に出す。
- 会社画面では、登録された受渡しの短い経路と他の活動を先に示す。活動を選ぶと、前の仕事・その活動・次の仕事を表示し、道具から逆方向にも辿れる。
- まだ活動に分類していない話も、実際の担当・道具・情報を含むカードとして見える。会社説明・全件一覧・分類編集は必要時に開く。
- 活動25業務、仕事の種類5業務、個別業務1業務という探索対象と範囲表示を揃えた。会社全体の蓄積303業務と、現行300・将来3の表示範囲を区別する。
- システムの名前・説明に一致する検索結果を優先し、同じ業務で使われる他の道具に検索結果が埋まらないようにした。名前の一致がない場合は、検索した仕事で使われる道具を示すと説明する。

## 初回入力から訂正・追記・保存

空の `novice-input-20261003` で、業務名を先に作らず次の3行を入力した。

```text
注文がメールで届く。
担当の人がExcelで「注文書」を確認する。
足りなければ生産管理にTeamsで相談している。
```

「流れを見る」で保存前の3手順が現れた。担当が不明な部分と、推定した接続・条件は要確認のまま表示された。2番目の手順で担当を「営業担当」、結果を「不足のある注文を区別し、生産管理への相談が必要か決まる」と訂正した。実行方法は勝手に確定しなかった。

SharePointへの保存を追記した後、本文をTeamsへの「確認結果」の送信に書き換えて再整理した。追加1・除外1と反映された位置を確認した。次に2番目の手順から `営業担当がOutlookで「確認結果」を生産管理へ送信する。` という続きを挿入し、追加1の手順に移ることと、前の句点・改行が書き換わらないことを確認した。訂正した担当と結果も保持された。

最終的に1業務・5手順を保存し、2回の保存履歴を確認した。本文だけを変更した状態では「未反映のメモあり」と表示され、再整理するまで保存できなかった。再読込後も、原文・営業担当・訂正した結果・人の訂正の表示が残った。会社画面には活動分類を求める前に、メール・Excel・Outlook・Teamsと注文書・確認結果を含む仕事が現れた。

`novice-mobile-20261003` では同じ3行を幅390pxの同一オリジンiframe内で操作した。候補表示後の流れへの切替、担当・結果の訂正、保存、メモへの復帰、再読込後の選択保持を確認した。本文の有効幅375px（縦スクロールバーを除く）と文書幅が一致し、入力画面全体の横はみ出しはなかった。実機のタッチ操作は検証していない。

## 300業務の探索

新しく生成した `novice-company-20261003` を使用した。現行300業務、将来3業務、12活動、60種類の仕事、30システム、370データ、計3029手順、310受渡しを含む。

実操作で次を確認した。

1. 全体の受注 → 生産計画 → 調達 → 製造 → 品質 → 配送と他6活動を見渡し、受注活動から25業務、受注登録の5工場、千葉工場の1業務へ進む。範囲表示も25 → 5 → 1になった。
2. 価格条件から確定受注価格、与信チェック、限度超過の保留、経理の解除判断と再判定・保留継続の分岐を読む。条件付きの接続を通常の直線として扱わない。
3. 受注から需要供給調整、MRP確認へ進み、「同じ仕事の続き」に送り元の手順と渡した情報が残ることを確認する。
4. システム一覧でSnowflakeを検索し、該当する道具を開く。会社側と「詳しく調べる」の双方で、現行の直接関連300業務・手順利用10・連携300という同じ内訳を確認する。内訳は重複を含み、合計300は業務IDで重複を除く。
5. 現状と将来案の比較で手動受渡し5 → 1、除外するExcel・メール転記、追加するAPI反映と版不一致の保留、その結果と根拠を読む。レポートプレビューにも結果・条件・次の業務・比較を含める。
6. 「改善後の案」に切り替えて3業務を表示し、現行だけの受渡しを混ぜない。会社全体の蓄積303と表示範囲3の区別を確認する。
7. 比較ビューの300業務・397資産を開き、12業務×20資産の範囲で表示する。次の12業務と検索を操作し、応答停止が起きないことを確認する。

ブラウザー操作・観測を含む単発の時間は、比較画面474ms、次の12業務481ms、検索242msだった。継続的な性能測定や応答時間の保証ではない。一般の会社でも固定のバリューチェーンがあるとは仮定せず、鳥瞰の矢印は登録された受渡しだけから作る。探索は最大6活動の経路に制限し、循環のある密なグラフでも組合せを無制限に展開しない。

## 自動検証・保全・残る制約

- `npm test`：76テスト成功。原文を壊さない追記、保存前の表示、受取情報、未確認の結果・接続、人の訂正、分類前の仕事、条件で空になる画面、密な循環グラフの鳥瞰、確度と人の確認を混同しない表示を含む。
- `npm run typecheck`、`npm run build`：成功。
- `npm run test:regression`：別SQLite・ポート3105で35ケース成功。API抽出・保存・履歴・再読込・条件・原文訂正などを含む。
- 変更前の7プロジェクトすべてについて、APIのgraph＋transcriptsのSHA-256、業務数、保存履歴数が変更後も一致した。既存の `chemical-demo` や過去の監査データを置換していない。

今回の入力検証はAI未接続の簡易抽出。UIで入力を確認・訂正する作業と、抽出精度を分けて評価した。OpenAI/Anthropicアダプターはモック応答の既存テストが成功しているが、実際のAI接続時の精度は未検証。簡易抽出は複雑な省略主語、合流、再開、業務境界を自動で確定できず、未確認として残る。

サンプルにも結果の未確認や共通の架空記録が残る。原文にない結果や接続を完成した事実として見せず、利用者が確認・補足する入口を保持した。未保存の話・候補はブラウザーのセッションに保持し、明示的に保存した原文・構造・訂正はSQLiteと保存履歴に蓄積する。

ローカルの証跡は `.data/qa-novice/` に保存した。`input-review.png`、`company-overview.png`、`mobile-flow.png` が最終画面、`ui-evidence.json` が操作時の画面テキストと時間、`preservation-before.json` / `preservation-after.json` が既存データの保全確認。幅390px用の一時HTMLと補助サーバーは検証後に片づける。
