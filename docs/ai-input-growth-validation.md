# 実AIで入力から構造を育てる検証

## 2026-10-03：最初の入力と訂正

本検証は独立した `ai-growth-20261003` プロジェクトを、業務0件からブラウザの入力画面で育てる。既存の300件サンプルを投入する検証とは別に扱う。接続先はローカルの公式 Codex App Server、指定モデルは **gpt-6-luna**。既存のChatGPTログインを利用し、認証情報は読み出し・保存していない。アプリの推論呼出しにツール・ファイル・Web・委任機能を与えない。

### 確認した入力と操作

1. 名前を先に決めず、「注文がメールで届く。担当の人がExcelで内容を見て、足りなそうなら生産管理にTeamsで聞く。誰が出荷してよいと決めるかはまだ知らない。」を入力。
2. 保存前に3手順、道具、情報の変化、原文、不足時の条件を確認。受取担当・メールからExcelへの移し方・出荷判断者は未確認のまま質問になった。保存して業務1件になった。
3. 質問へ、営業が数量と納期を手で転記して不足数量を決め、生産管理がTeamsで受け取り製造必要量を決めると追加回答。MRPは別の仕事として後で説明すると明記。4手順へ更新され、1追加・3変更を確認して保存。
4. 不足数量の結果を、人が「受注数量と倉庫の在庫から、不足数量を確定する」と訂正。
5. 本文を訂正し、Excelは現在使わずSharePointの受注確認表へ手で転記すると説明。再整理し、人の結果の訂正とSharePointへの変更が両立することを確認。
6. この操作で、AI由来の古い詳細手順にExcelが残る不具合を発見（Issue #28）。抽出元と人の訂正を区別する処理へ修正し、同じ本文で再整理。詳細手順もSharePointへ更新され、原文、過去の回答、人の訂正、未確認事項を保ったまま3回目の保存が成立した。

旧回答にExcelが残ることは履歴として保持し、最新本文との訂正を注意事項で説明する。出荷可否の判断者は未確認、MRPはこの説明の対象外として残った。曖昧な話を、架空の完成済み業務へ置き換えていない。

### 修正と検証の区別

- 入力前に、未設定・設定済みで応答未確認・この画面で応答成功・失敗を区別する。保存した構造には抽出したモデル名を保持。
- 300件を扱う抽出コンテキストは、最初の30件固定から、入力に関係する候補を選ぶ方式へ変更。現行/将来の範囲を分け、最大12業務・各6手順・System/Data各30候補に制限。
- AIの失敗で原文や候補を消さず、認証・時間切れなどを安全な文言で伝える。API応答本文や認証情報をログへ出さない。
- 人の訂正は保持する。AIが作った詳細は最新の説明で更新する。抽出元が不明な旧データの詳細は保守的に保持し、その保護理由を次の改訂にも引き継ぐ。
- 自動テスト84件、API回帰35件、型検査と本番ビルドが成功。ここに含む300件の検索テストは合成したグラフの単体検証であり、300件の実AI入力が成功した証拠ではない。
- 既存10プロジェクトについて、構造・原文のSHA-256と業務数・改訂数が検証前後で一致した。

操作記録と画像は無視対象の `.data/qa-ai-growth/` に保存する。

## 2026-10-04：新しい話から全体像と業務の接続を育てる

独立プロジェクトを入力画面の実AIで **0→1→2→3→4→5業務** と増やした。会社の分類を先に登録する操作や、完成グラフの投入は使っていない。

### 確認した入力と操作

- 最初の注文の話を再整理し、題名・会社の活動・仕事の種類を保存前に表示。「注文に応える／注文内容の確認」と人が訂正して保存した。
- 「さっきの注文確認で生産管理が決めた製造必要量を受け取る」から、SAPへの登録、MRPの自動計算、購買依頼案、調達回答までの計画保留、製造指図案の確定を入力。既存の注文の製造必要量決定から、新しい登録手順への受取候補を確認した。受取元を開くと送り出す手順へ移り、その手順からMRPの受取手順へ戻れることを操作した。
- 「さっきのMRPでできた購買依頼案」から、SAP→CSV→Excel、メールでの見積りと納期確認、SharePoint保存、購買課長の発注先判断を入力。調達可能ならTeamsで回答し、MRPの製造指図案の確認へ戻る。調達不可では発注せず保留する。回答のリンクを実際に開いて、MRPの先頭ではなく再開対象の手順に着くことを確認した。
- 原料受入検査を入力し、購買で作った原料発注書への参照を、通知・転送の受渡しと区別して確認。数量・ロットの照合、仮受入、検査依頼、分析機器→LIMSの自動送信、LIMSの規格判定、規格内の使用可承認・SAP在庫更新、規格外のQMS不適合票・隔離を確認した。再検査の許可者や不一致時の行先は未確認のまま残る。
- 製造計画の指図と検査後の原料ロットから製造を開始する話を入力。SAP→MESのCSV、人の原料投入、DCSの自動制御、DCS→MESのAPI自動送信、反応逸脱時の保留と製品検査依頼を確認して保存した。上流の情報の対応に推定が残る箇所は、確定した受渡しへ置き換えていない。

### 実AIで発見して修正した問題

原料検査の照合手順に、照合結果である「一致した場合」が実施条件として付いていた。後の登録条件を、先行する照合の条件にしないよう指示を修正し、同じ本文の再整理で解消を確認した。

製造では「原料使用不可」と「反応条件逸脱」が同じ検査へ誤接続された。再整理後にも原文にない自己ループが出たため、異なる例外を分ける指示と、原文の再実行記述で確認できないAIの自己ループを保留し質問へ残す処理を追加した。同じ本文の再整理で、原料の着手停止と反応後の保留が別の説明となり、架空の再開線が消えたことを確認した。これらの誤った候補は保存していない。

分類とSystemの役割は整理案として根拠とともに保存する。原文にない会社名、担当部署、基盤依存や業務順序は追加しない。人の分類の訂正と、独立して登録された既存分類をAIが置き換えない。接続には確認元の業務を持たせ、新しい受取側の話で記録した接続が、送り出す業務の再保存で消えないようにした。

全体像のSAP詳細で、入力ごとの役割が分類未設定を理由に落ちる問題も発見した。分類が不明でも役割を保持し、表示範囲内の業務ごとの役割と原文を表示するよう修正。曖昧な別名を特定のSystemへ割り当てず、初期表示を3業務に制限した。

Teamsから調達回答の手順を開くと、記録済みのMRPへの接続が「次の接続は未登録」と表示され、下の折り畳みへ隠れていた。会社側の読み取り画面にも、選択手順の受渡し・情報参照を表示するよう修正した。受取側の情報表示とデータ追跡にも、記録された業務間接続を含める。業務間の受取と、システム内の参照・更新の操作は区別し、記録された再開手順と同じ情報を保って業務をまたぐ。

会社全体→システム・道具→Teams→調達可能の回答→MRPを操作し、MRPの4番目の再開手順・調達可能との回答・購買側の出発手順・表示粒度が残ることを確認。文脈の戻るボタンでも購買の6番目へ戻った。業務をまたぐ際には、続きの流れが画面内に見える位置へ移動する。

自動テスト92件、API回帰35件、型検査を含む本番ビルドが成功。自動テストでは、受取・参照の違いのSQLite保存、別シナリオや架空の業務IDの拒否、人の訂正保持、原文にない自己ループの保留、分類未確認でも役割を保持する処理を確認する。これらは実AI抽出精度の測定とは分ける。5業務・9改訂の時点でも、既存10プロジェクトの構造・原文のハッシュと業務数・改訂数は一致した。

### 残る課題

8手順の原料検査ではmedium設定が120秒で時間切れになった。メモと候補は残り、簡易抽出に切り替わらなかった。low設定の再試行・再整理は約76〜77秒、複雑な製造の再整理は約92〜101秒で完了した。処理の初期化は約0.3秒で終わっており、待ち時間の大部分は推論と応答生成である。待ち時間と蓄積時の共有資産対応づけはIssue #32で改善を続ける。

購買の話にTeamsでの回答方法を書いても、以前のMRPの「誰がどの方法で回答するか」という確認事項はそのままだった。新しい話と既存の未確認事項・矛盾を照らす処理はIssue #31に残す。

## 2026-10-04：6件目の製品検査と待ち時間の改善

製造課から製品ロット・製造実績を受け取るメモを入力し、6件目の製品出荷前検査を保存した。分析機器→LIMSの自動送信、LIMSの合否、合格時の品質管理課長の出荷可承認とTeams通知、不合格時のQMS不適合票・ロット保留を確認した。解除条件は未確認として残る。Systemの「検査・品質管理」の分類案と役割を原文付きで確認した。整理は約59秒、保存時の対応づけは約5秒。6業務・10改訂まで画面の実AI入力で増えている。

再整理では、業務メタデータに含まれる古い構造を二重に渡さず、前の候補を安定した手順キー・概要・人の訂正・除外に絞った。完全な原文と追加回答は保持し、人の訂正と詳細を保存する処理は変えない。共有資産の照合は表示する状態を揃え、最大60件の関連候補へ制限。候補の不在や検索順位で同一性を確定しない。登録順の遅い資産や曖昧な別名の検索は合成データのテストで確認し、実AIの300件検証とは区別する。

処理中は、話の整理と保存時の道具・情報照合を区別し、経過秒と候補を保っていることを表示する。待ち時間の改善を、抽出内容が正しくなった証拠として扱わない。

同じ製造メモの再整理では入力コンテキストを減らし約82秒で応答したが、原料照合から製品検査へ情報を渡す線と、逸脱による保留から正常完了へ進む線が出た。この候補は保存しなかった。AI由来の受渡しで情報と送り出す手順の出力が一致しない場合、また条件付き保留の解除・再開を原文で確認できない場合は、接続を保留して確認事項に残す処理を加えた。保留後の原文にある通知・依頼と、人の明示的な訂正を保護する。

別の条件の枝を一覧上で「接続は未確認」と見せる問題はIssue #34に残す。

入力コンテキストを減らした後にも約102秒かかった再整理があり、速度の改善は安定していない。通常経路の欠落もあったため、前の接続を比較情報に残し、本文の記述順に根拠がある通常経路を推定として示す指示を追加した。同じ本文を再整理した約95秒の応答では、投入→DCS制御→MES送信の通常経路、逸脱の保留と逸脱なしの実績確定の別々の枝を画面で確認した。保留から正常完了への線や、原料照合から製品検査へ渡す線は出ていない。接続の推定と再開先の未確認は残る。この再整理候補は比較検証用の保存前の候補として保持し、既存の保存結果を上書きしていない。

自動テスト99件とAPI回帰35件、型検査を含む本番ビルドは成功しているが、AIの品質や待ち時間のIssue #32は完了扱いにしない。
