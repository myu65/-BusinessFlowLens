# 入力と図を見ながら仕事の構造を育てる

新しい話は、業務名を決めずに書ける。「話しながら整理」と「まとめて書く」は同じ本文を使うため、切り替えても文章は残る。資料を使う場合は「資料・画像を読み込む」から始める。初回は入力と図の例を並べ、まだ使わない手順の詳細欄を表示しない。

図ができた後は、「この流れを育てる」に入力する。「話を足す・直す」と「未確認に答える」を切り替えて使う。話の対象、確認事項、図で選んだ追加場所を入力欄の上に示す。

| やりたいこと | 入力する場所 |
| --- | --- |
| 続きを話す、担当などを訂正する、つなぐ・まとめる操作を頼む | 「話を足す・直す」 |
| 読み取りで分からなかった点に答える | 「未確認に答える」。確認事項の一覧の「この確認に答える」からも開ける |
| 矢印の間に作業を追加する | 図の＋を選ぶ。同じ入力欄で、追加前後の手順を見ながら書く |
| 操作案へ返答する | 通常の入力欄が操作案と返答欄へ切り替わる。案を採用するか取り消せる |
| 項目を直接直す、矢印を編集する | 選んだ手順の編集ボタンから開く。編集中は通常の話の入力を休止する |
| 元の本文を書き直す | 「元の話を読む・書き直す」。変更を図へ反映してから保存する |
| 別の話を探す | 「保存した話・下書きを探す」の検索欄。表示は6件ずつ |

話と回答の書きかけは別々に保持する。切り替えても最後に選んだ確認事項へ戻れる。「書きかけを取り消す」は表示中の入力だけを消す。追記は「あとで続ける」で場所と文章を残し、「途中の追加を続ける」から再開できる。

分からない質問を後回しにしても、業務の事実として回答した扱いにはしない。答えられる質問が残っていなければ通常の入力へ戻り、確認事項と履歴を残す。図からの追加や直接編集、原文の書き直しは、入力中の別の作業と重ねて反映しない。保存時には未反映の本文・回答・追記・訂正を確認する。

## 検証

既存のプロジェクトとは別のSQLiteに、空のプロジェクト、品質業務、303業務の化学メーカーを用意した。ブラウザーで次の操作を行った。

「注文がOutlookで届きます。誰かがExcelで内容を確認して、営業担当がSAPへ受注を入力します。その後の担当はまだ分かりません。」から、gpt-6-lunaで3手順の候補を作った。業務名の事前入力は不要で、不明な担当と受注入力後の作業を確認事項として残した。回答で担当を補足し、確認結果を直接編集してから、選んだ手順の担当を対話で訂正した。本文にTeamsで生産計画担当へ知らせる話を加えると4手順になり、人が編集した確認結果も残った。

品質業務では、図の矢印から「品質担当がSharePointで検査値の原記録を照合する。」を入力した。中断・再開で文章を保持し、実AIで1手順を追加した。前後の接続、元の条件分岐、再調整からの戻りを図で確認した。名前変更の対話では、通常の入力欄が操作案への返答欄に切り替わり、取消で元の名前へ戻ることを確かめた。

303業務では受注登録を検索し、保存済みの業務フロー、会社の鳥瞰、システムの鳥瞰を開いた。現在の仕事300件と将来案3件を持つデータで、検索と画面の移動が応答した。サイドパネルの803px幅でも、図の＋から入力へ戻り、追記を中断・再開・取り消せることを確認した。

自動テストでは、一つの入力欄で回答と対話を切り替えること、消えた確認事項へ回答しないこと、検索を重複させないこと、操作案の返答と通常の対話を同時に出さないこと、分岐を指定するまで追加を実行しないことを確認する。既存の保存・訂正・根拠・履歴のテストも実行する。

303業務は表示と探索の検証用のサンプルであり、実AIで300業務を読み取った結果ではない。今回のUI変更では抽出処理やPDFの読み取り方式、Snowflakeの保存形式を変更していない。書きかけを保持する範囲は既存の保存方式に従う。対話の補足・訂正は入力方法の切替で保持するが、ページの再読み込みをまたぐ永続化は保証しない。
