# 鳥瞰で何をどう見るか

鳥瞰の目的は、業務の目的・範囲と共通データの接点を捉え、確認や改善の入口を選べること。

## 調査と画面への反映

データ総研「[データアーキテクチャの策定](https://jp.drinet.co.jp/blog/datamanagement/oldgr7rdvubdu)」（2021-02-25）は、現状の粗い概念データモデル、業務／システムとの関連、業務共通／個別、類似データの比較を重視する。また、名称の感覚的な統一ではなく、識別子と値の対象範囲を確認する必要を説明している。

「[業務モデルとシステムモデル](https://jp.drinet.co.jp/blog/datamanagement/olda7m3zhsbnl)」（2018-08-31）は、業務の実体とシステムのテーブルなどの違いを説明している。

以下は記事を踏まえた本アプリの設計判断であり、記事そのものの画面仕様ではない。

| 利用者が知りたいこと | 表示・操作 |
| --- | --- |
| 今の業務か将来案か | 現状・将来案・代替案を切替。未指定の既存業務は現状扱い。全案は比較用と明記 |
| 何を始め、何を達成するか | 業務カードの概要、開始条件、成果、担当 |
| どのデータが業務の接点か | 業務データ×業務の表。参照／登録・更新／送信／利用／受け渡しを区別 |
| 共通か個別か | 表示対象内で同じ保存データに関わる業務数で分類。全社共通であることの保証ではない |
| どのシステムが関係するか | データ選択時に明示された直接関連とシステム間受け渡し、その根拠を表示 |
| 何を確認すればよいか | 要確認状態、意味・正本・管理責任・識別子・対象範囲の確認案内 |
| 具体的にどう進むか | 関連業務の手順へ移動。技術情報は詳細レベルで閲覧 |

## 解釈の境界

- 同じ業務でシステムとデータを使っても、保存先・正本・連携とは推定しない。
- 複数システムとの関連は重複や不整合の証明ではない。役割と同一性を確認する入口とする。
- 名称だけで自動統合しない。既存の明示的な資産統合で人が確認する。
- 未記録の業務間受け渡しや概念上のデータ間関係は描かない。順序線をデータ利用として数えない。
- 業務データと物理テーブルを分ける。現在のモデルには識別子・活動定義域・正本の専用フィールドがないため、鳥瞰で確定済みと表示しない。意味や範囲は既存の説明・メモに補足できる。
- 表示切替は保存グラフを変更しない。根拠のステータスは保持し、未確認も見えるようにする。

## 検証

`tests/overview.test.ts` でシナリオ分離、管理先の非推定、受け渡し由来の業務関係、不正な順序線の除外、空状態、グラフ不変を確認する。既存の保存・統合・技術詳細テストも合わせて実行する。
