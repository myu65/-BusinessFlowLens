## 入力からの実操作

検証データは `input-validation-first-20261003` と `input-validation-memo-20261003` に独立して作成した。

最初の曖昧なメモ：

> 注文がメールで届く。担当の人がExcelで確認する。足りなければ別の部署に相談している。

3手順の候補が出る。担当・部署・情報名・結果を補完せず未確認にする。「足りなければ」は条件として抽出し、接続を推定として表示する。

2番目の手順の後に「営業担当がTeamsで『確認結果』を送信する」という話を追加し、追加したカードへ移った。その手順を除外して再整理しても除外を保持した。Excel確認には営業担当・営業部を補足し、希望数量と在庫の一覧を根拠に不足の有無を区別して生産管理への相談を動かす、という結果を人の訂正として記録した。保存後の再読込とv1の履歴で、原文・補足結果・除外を確認した。

さらに、この業務の原文に未保存の確認回答を追記したまま、新しい話「生産計画担当がTeamsで『計画案』を受け取る」を保存した。元の業務に戻ると入力途中の原文が残り、APIの保存済み原文には未保存の追記が混ざっていないことを確認した。保存は選んだ構造の原文に限定する。

もう一つのメモ：

```text
営業部の佐藤さんがメールで「注文書」を受け取る。
佐藤さんがExcelで「受注確認リスト」を作成する。
佐藤さんがExcelから「受注確認リスト」をSAPへ手動で転記する。
SAPが自動で在庫を確認する。
在庫が不足する場合、佐藤さんはTeamsで生産管理部に納期の調整を依頼する。
在庫がある場合、SAPから「出荷指示」をWMSへAPIで自動送信する。
```

保存前に6手順、原文の人・道具・情報・自動処理、在庫確認からの二つの条件付き候補を確認した。通常の順次接続と条件接続は推定であり、担当者が接続を確認するまでは確定扱いしない。追加回答後に本文のExcelでの作成をSharePointへ訂正して再整理し、最新本文と人が補足した在庫判断結果が両方残ることを確認した。Teamsの転記完了通知を追記して7手順とし、保存・再読込まで実施した。

自由な追加回答は原文と別に保存する。AI未接続の簡易抽出では自由回答を業務意味に安全に変換できないため、質問を回答済みとして消さず、本文への補足または構造の直接訂正で反映するよう画面で案内する。

## 再現と制約

アプリを起動し、`/?projectId=input-validation-first-20261003` で入力例、`/?projectId=input-validation-company-v2-20261003` で補強したサンプルを開ける。

新しい検証プロジェクトを作る場合は、既存にない名前を指定する。

```powershell
npx tsx scripts/seed-chemical.ts --project-id=my-new-validation-project
```

既存名への投入は標準では拒否する。人の未保存の話と候補はブラウザーのセッション内に保持し、明示的に保存した構造・原文・修正・除外・追加回答はSQLiteと履歴に蓄積する。

簡易抽出は主に1文1手順と明示的な語句に基づく。省略主語、複雑な業務境界、自由な条件・合流・再開を自動で確定できない。曖昧な受取先は確認事項のまま残す。AI接続時の複雑な日本語の理解と、蓄積された多数の業務から正しい接続を選ぶ精度は別途評価が必要。

サンプルの具体化は主に受注・需給調整とExcel・groupware・分析連携の意味、保留・再開に行った。他の業務には共通の架空記録や結果未確認の箇所が残る。登録されていない結果や接続を、実際の会社の確定済みの説明として表示しない。
