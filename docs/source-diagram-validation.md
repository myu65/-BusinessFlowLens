# 原図と業務の流れを一緒に確認する

PDF・Office資料のページ画像を読む処理と、業務構造を作る処理は別だった。読み取り文章を経由するだけでは、元の矢印・分岐・戻りを確かめ直せない。構造化・再整理・言葉での訂正にも、選択した元ページの画像をサーバー側から直接渡す。3ページずつ読み、次のまとまりには前の候補を渡す。選択ページを黙って省略しない。

図からの解釈は推定のまま保持する。手順・関係に資料IDとページIDを持たせる。存在しないページ・別プロジェクト・原本ハッシュの不一致は参照できない。画像の説明を原文の引用として表示しない。

入力画面では元ページ、原本の取得、読み取りとの比較、言葉での補足・訂正を開ける。変更前後を確認してから保存する。訂正した項目だけが以前の人の訂正より新しい根拠となり、関係のない訂正は保持する。業務名はその場で変えられ、工場名は別に表示する。会社の詳細画面でも入力画面と同じフロー図を使い、同じ手順と元資料を開ける。

自動テストでは、4ページが3枚・1枚で実際の画像リクエストに渡ること、参照の範囲、推定の保持、SQLiteへの保存、会社側のフロー図、人の訂正の更新と保護を確認する。実モデルでの読解精度は独立した資料を操作して別に確認する。

## 実際の入力と操作

2026年10月5日、既存データを残して、`pdf-arrows-20261005`と`pdf-diagram-first-20261005`でgpt-6-lunaを使った。画像だけの3ページPDFを画面から読み込み、ページの読解と業務候補の構造化をそれぞれ実行した。

- 受注図の1・2ページを選択し、元画像2枚を直接参照して11手順の候補を作った。共通の受注入力・価格決定・与信判定は一組にまとめ、TeamsとOutlookの異なる解除依頼は採用版が未確認の記載差として表示した。業務上の確定した分岐と区別した。
- 委託検査図の3ページに対し、「購買担当がOutlookで受け取り、Teamsで品質担当へ渡してからLIMSへ登録する」と訂正した。6手順になり、追加したTeamsの引き渡しと担当の変更を保存前に確認した。外部検査会社の内部は見えないこと、成績書の受取だけでは合格にならないことを保った。
- 「名前を直す」で「委託検査を依頼して成績書を受け取る」に変更して保存した。会社の詳細画面でも同じ6手順の図を開き、手順4の購買担当と元PDFを確認した。
- 「受取担当だけ営業事務担当へ訂正する」の実操作で、関係ない手順名までAIが書き直す問題を発見した。訂正項目の指定にない内容を既存の候補から保つ処理を追加した。選んだ手順への訂正では、他の手順と接続も保持する。自動テストには、モデルが無関係な改名・接続の削除を返す場合を追加した。
- 保存前の「今回の補足・訂正を取り消す」で、保存済みの購買担当とTeamsの引き渡しを含む6手順へ戻せた。
- 初回の資料からの構造化中にも元PDFを表示できた。AIの応答失敗時にも元資料と再試行の入口を残した。

310件の単体テスト、48件のAPI回帰テスト、型検査、production buildを実施した。元からあった10プロジェクトの業務構造・原文・履歴数は変わっていない。

## 残っている検証

画像の解釈はモデルの推定であり、正しさの保証ではない。ページ間の記載差が現行版・旧版の違いなのかは、資料に明記されない限り利用者が確認する。保留中の解除依頼を再開と誤って表示する候補はIssue #157で別に修正する。重複した保存済み業務の統合はIssue #160で扱う。どちらも今回できたと報告しない。

# 保存先を変える場合

現在は原本と派生ページ画像をプロジェクトのSQLiteに保存する。業務構造には物理ファイルパスを入れず、`documentId`・`unitId`と原本ハッシュを持たせる。画面とAIはRepository経由で原本・画像を取得する。

Snowflakeをバックエンドにする場合は、原本とページ画像をステージに保存し、資料・ページの論理IDから保存先へ対応付ける。原本ハッシュと変換の版を保持し、変更したファイルを過去の根拠に上書きしない。ステージの位置や認証情報をGraphやAIの回答へ埋め込まない。プロジェクトの読取権限を確認してから取得し、AIへ渡すときもその参照の範囲を守る。SQLiteのBLOBとSnowflakeのステージはRepositoryの実装で切り替える。今回Snowflakeへの接続は行っていない。
